# 🌾 Royal Fields Database System

A relational database for **Royal Fields**, a community-supported agriculture (CSA) initiative in Limpopo, South Africa. The system connects small-scale farmers with local consumers by managing subscriptions, produce inventory, deliveries, payments and farmer relationships.

## Background

Royal Fields operates in select areas of Limpopo Province. Members subscribe to receive weekly or bi-weekly boxes of seasonal, culturally relevant produce (for example Amaranth/Morogo, Okra and Mango), supplied by independent local farmers. Royal Fields staff coordinate farmers, manage subscriptions, plan delivery logistics and handle financial transactions.

**Problems the database addresses**

- Logistical challenges across Limpopo's large geographic area
- Limited supply and quality-control capacity among small-scale farmers
- Unreliable market access for small farmers
- Varying technology adoption among farmers and consumers
- Limited funding, so the solution must be low-cost and usable by people with basic computer skills

## Project Objectives

- Automate subscription management, inventory tracking and farmer communication
- Store all operational data in one centralised database
- Track payments accurately and support financial reporting
- Support delivery planning and route optimisation
- Remain extensible for future growth

## Database Design

The design follows the Phase 2 ERD and logical model, normalised to **Third Normal Form (3NF)**.

- 12 tables, all using surrogate numeric primary keys generated by Oracle sequences
- Lookup tables (`DELIVERYSTATUSLOOKUP`, `PAYMENTTYPELOOKUP`, `SUBSCRIPTIONTYPELOOKUP`) standardise categorical values
- `BOXCONTENT` is a bridge table resolving the many-to-many relationship between `DELIVERY` and `PRODUCE`
- `CHECK` and `UNIQUE` constraints enforce data validity (non-negative amounts, valid frequencies, unique phone/email, etc.)
- `TOTAL_DELIVERIES` on `SUBSCRIPTION` is a derived attribute, computed at query time rather than stored

## Tables

| Table | Purpose | Key Foreign Keys |
|-------|---------|------------------|
| `DELIVERYSTATUSLOOKUP` | Delivery statuses (Scheduled, In Transit, Delivered) | none |
| `PRODUCE` | Produce catalogue: name, variety, unit, price, storage, organic flag | none |
| `FARMER` | Participating small-scale farmers and their details | none |
| `INVENTORY` | Stock supplied by farmers: quantity, harvest and expiry dates | `FARMER_ID`, `PRODUCE_ID` |
| `PAYMENTTYPELOOKUP` | Payment methods (Credit Card, Bank Transfer, Cash) | none |
| `SUBSCRIPTIONTYPELOOKUP` | Subscription plans (Standard, Premium) and prices | none |
| `MEMBER` | Customers who subscribe to produce boxes | `SUBSCRIPTION_TYPE_ID` |
| `SUBSCRIPTION` | Member subscription: dates, delivery day, frequency, box size | `MEMBER_ID` |
| `ROUTE` | Delivery routes, areas, drivers and estimated times | none |
| `DELIVERY` | Individual deliveries to members | `MEMBER_ID`, `ROUTE_ID`, `DELIVERY_STATUS_ID` |
| `PAYMENT` | Member payments and farmer payouts | `MEMBER_ID`, `FARMER_ID`, `PAYMENT_TYPE_ID` |
| `BOXCONTENT` | Produce items and quantities in each delivery | `DELIVERY_ID`, `PRODUCE_ID` |

### Notable constraints

- `SUBSCRIPTION.DeliveryFrequency` must be `'Weekly'` or `'Bi-Weekly'`
- `PRODUCE.Organic` is `NUMBER(1)`: `0` = No, `1` = Yes (Oracle has no boolean type)
- `INVENTORY.QuantityAvailable >= 0`, `PAYMENT.Amount >= 0`, `BOXCONTENT.Quantity > 0`, `SUBSCRIPTIONTYPELOOKUP.Price >= 0`
- `FARMER.Phone`, `FARMER.Email`, `MEMBER.Phone` and `MEMBER.Email` are unique
- `PAYMENT.MEMBER_ID` and `PAYMENT.FARMER_ID` are nullable, so one table records both member payments and farmer payouts

## Relationships and Business Rules

Key rules from the Phase 2 design:

- A member has one or more subscriptions, and each subscription belongs to exactly one member
- Each subscription specifies a weekly or bi-weekly delivery frequency
- Farmers must supply at least one batch of produce, recorded in inventory
- Every delivery is assigned to a member, a route and exactly one status
- A route may have no deliveries scheduled yet
- A member may have no deliveries yet (for example a new member)
- Payments use one predefined payment type, and some payment types may be unused
- Each subscription type must be used by at least one member

## Getting Started

### Prerequisites

- Oracle Database (the project was built and tested with Oracle)
- Oracle SQL Developer (or any Oracle-compatible SQL client)

### Setup

1. Connect to your Oracle schema in SQL Developer.
2. **Drop existing objects** (child tables first to avoid foreign key conflicts). This deletes all existing data, so do not run it against a production schema:

   ```sql
   DROP TABLE BOXCONTENT;
   DROP TABLE PAYMENT;
   DROP TABLE DELIVERY;
   DROP TABLE SUBSCRIPTION;
   DROP TABLE MEMBER;
   DROP TABLE ROUTE;
   DROP TABLE INVENTORY;
   DROP TABLE FARMER;
   DROP TABLE PRODUCE;
   DROP TABLE SUBSCRIPTIONTYPELOOKUP;
   DROP TABLE PAYMENTTYPELOOKUP;
   DROP TABLE DELIVERYSTATUSLOOKUP;
   ```

   Then drop the matching sequences (`DeliveryStatusID_value`, `ProduceID_value`, `FarmerID_value`, `InventoryID_value`, `PaymentTypeID_value`, `SubscriptionTypeID_value`, `MemberID_value`, `SubscriptionID_value`, `RouteID_value`, `DeliveryID_value`, `PaymentID_value`, `BoxContentID_value`).
3. **Create the tables and sequences** in dependency order: lookup tables, `PRODUCE`, `FARMER`, `INVENTORY`, `MEMBER`, `SUBSCRIPTION`, `ROUTE`, `DELIVERY`, `PAYMENT`, `BOXCONTENT`.
4. **Insert the sample data** (see below).
5. **Create the views and indexes.**
6. Run the SELECT, UPDATE and DELETE statements to explore the data.

### Sequences

Each table has a sequence (e.g. `MemberID_value`) that generates its primary key via `.nextval`. Sequences start at 1, increment by 1 and use `CYCLE`.

> ⚠️ **Note:** `CYCLE` restarts a sequence at 1 after its maximum (100 for lookup tables, 1,000 for produce, farmers and routes, 10,000 for inventory, members, subscriptions, deliveries, payments and box content). At that point duplicate keys become possible, so monitor key usage as the data grows.

Indexes were added on foreign key columns used frequently in joins:

```sql

CREATE INDEX idx_delivery_member     ON DELIVERY(MEMBER_ID);
CREATE INDEX idx_inventory_produce   ON INVENTORY(PRODUCE_ID);
```

**Example: deliveries per route, flagging inactive routes**

```sql
SELECT
    r.RouteName,
    COUNT(d.DELIVERY_ID) AS DeliveryCount,
    CASE
        WHEN COUNT(d.DELIVERY_ID) > 0 THEN 'Active'
        ELSE 'Inactive'
    END AS RouteStatus
FROM ROUTE r
LEFT JOIN DELIVERY d ON r.ROUTE_ID = d.ROUTE_ID
GROUP BY r.RouteName
ORDER BY DeliveryCount DESC;
```

**Example: stock status by produce**

```sql
SELECT
    p.ProduceName,
    i.QuantityAvailable,
    CASE
        WHEN i.QuantityAvailable = 0 THEN 'Out of Stock'
        WHEN i.QuantityAvailable < 20 THEN 'Low Stock'
        ELSE 'In Stock'
    END AS StockStatus
FROM INVENTORY i
JOIN PRODUCE p ON i.PRODUCE_ID = p.PRODUCE_ID;
```

## Scope and Limitations

**In scope:** the core database design and implementation covering member subscriptions, farmer information, produce inventory, delivery logistics and financial transactions, with basic reporting.

**Out of scope:**

- User interface, website or mobile app
- Real-time vehicle tracking
- Online farmer training modules

Project constraints: no budget for paid software, a single-semester timeframe, and an operation that must be manageable by people with basic computer skills.
